1. Learning Overview

An architecture pattern is a reusable way to divide responsibility, control execution and move information through an agentic application.

Explain why a complex task needs planning or delegation.
Trace a Reason → Act → Observe loop.
Differentiate supervisor and hierarchical supervisor systems.

Trainer principle: Start with deterministic Python demonstrations. Add an LLM only after learners can identify the planner, executor, tool, worker, state and exit condition.

2. Running Use Case: Amazon Settlement Reconciliation

Amazon sends a settlement record. The company must map Amazon’s SKU to the internal ERP SKU, find the ERP invoice, calculate the difference and decide whether the transaction is safe to match automatically.

Variance % = |Invoice Amount − Net Settlement| ÷ Invoice Amount × 100
Boundary rule: If variance is 5% or less, mark it MATCHED. If it is above 5%, route it to HUMAN_REVIEW.

3. Planner–Executor Pattern

A planner converts a goal into an ordered list of tasks. An executor performs those tasks one at a time and records each result in shared workflow state.

Planner–Executor topology
Business goalReconcile SET-1001
→
PlannerCreate ordered steps
→
ExecutorRun each step
↔
Tools & stateData, mapping, ERP
→
ResultMATCHED

Dynamic planning for the settlement

  1. Load settlement SET-1001.
  2. Map Amazon SKU to ERP SKU.
  3. Retrieve the ERP invoice.
  4. Calculate amount and percentage variance.
  5. Apply the threshold and produce a decision.
What is “dynamic”? A model-driven planner may change the plan after observing missing data or a failed task. A classroom demo can begin with a fixed plan so the control flow is predictable, then explain how Magentic orchestration adds manager-driven planning and replanning.

Runnable offline Python

01_planner_executor.py — essential pattern
class PlannerAgent:
    def create_plan(self, settlement_id):
        return [
            "load_settlement",
            "map_sku",
            "retrieve_invoice",
            "calculate_variance",
            "make_decision",
        ]

class ExecutorAgent:
    def execute(self, step, state):
        if step == "map_sku":
            amazon_sku = state["settlement"]["amazon_sku"]
            state["erp_sku"] = SKU_MAP[amazon_sku]
        elif step == "calculate_variance":
            invoice = state["invoice"]["invoice_amount"]
            paid = state["settlement"]["net_settlement"]
            state["variance_pct"] = abs(invoice - paid) / invoice * 100
        elif step == "make_decision":
            state["decision"] = (
                "MATCHED" if state["variance_pct"] <= 5
                else "HUMAN_REVIEW"
            )

state = {"settlement_id": "SET-1001"}
for step in PlannerAgent().create_plan("SET-1001"):
    ExecutorAgent().execute(step, state)

Visible execution trace

[PlannerAgent] GOAL RECEIVED: Reconcile SET-1001 [PlannerAgent] PLAN: load → map → retrieve → calculate → decide [ExecutorAgent] EXECUTING: load_settlement [ExecutorAgent] EXECUTING: map_sku [ExecutorAgent] EXECUTING: retrieve_invoice [ExecutorAgent] EXECUTING: calculate_variance [ExecutorAgent] FINAL RESULT: MATCHED

Use it when

  • The goal can be decomposed, but the exact plan may vary.
  • Tasks have dependencies and must run in order.
  • You need clear plan inspection, retry and re-planning.
Avoid unnecessary AI planning: If every step is always known and fixed, a normal deterministic workflow is usually simpler, faster and easier to audit.

4. ReAct Pattern

ReAct interleaves a decision with a tool call and its observable result. The agent repeats the loop until it has enough evidence or reaches a guardrail.

Reason → Act → Observe loop
1. DecideWhat information is missing?
→
2. ActCall approved tool
↑
↓
4. Final / repeatEnough evidence?
←
3. ObserveRead tool output
Safe teaching language: Display concise decision summaries and tool-call traces—not hidden private chain-of-thought. For example: “ERP SKU required” → call mapping tool → observe result.

Scenario: missing SKU mapping

DECISION An ERP SKU is required before invoice lookup. ACTION find_sku_mapping("AMZ-LAP-101") OBSERVATION "ERP-LAPTOP-501" DECISION The matching ERP invoice is now required. ACTION get_erp_invoice("ERP-LAPTOP-501") OBSERVATION {"invoice_amount": 1000.00} FINAL MATCHED

Runnable offline Python

02_react_pattern.py — bounded tool loop
def find_sku_mapping(amazon_sku):
    return SKU_MAP.get(amazon_sku)

def get_erp_invoice(erp_sku):
    return ERP_INVOICES.get(erp_sku)

erp_sku = None
invoice = None
max_iterations = 5

for iteration in range(max_iterations):
    if erp_sku is None:
        print("DECISION: ERP SKU required")
        erp_sku = find_sku_mapping("AMZ-LAP-101")
        print("OBSERVATION:", erp_sku)
        if erp_sku is None:
            decision = "HUMAN_REVIEW"
            break
        continue

    if invoice is None:
        print("DECISION: ERP invoice required")
        invoice = get_erp_invoice(erp_sku)
        print("OBSERVATION:", invoice)
        if invoice is None:
            decision = "HUMAN_REVIEW"
            break
        continue

    decision = "MATCHED"
    break
else:
    decision = "HUMAN_REVIEW"  # loop guardrail

Shipping variance lookup example

If the settlement contains a shipping deduction, the agent can call get_shipping_policy(order_id), observe the allowed fee, compare it with the charged fee and then stop or escalate.

5. Supervisor Topology

A supervisor understands the overall goal and delegates specialist tasks to worker agents. Workers focus on their own responsibility and return structured results.

Supervisor delegates to specialized workers
Supervisor AgentRoute, coordinate, aggregate, escalate
Extraction AgentRead settlement fields
Matching AgentMap SKU and compare
Validation AgentApply threshold

Responsibility boundary

ComponentKnowsDoes not need to know
SupervisorGoal, worker capabilities, routing and completion rulesDetailed extraction or matching implementation
Extraction workerSettlement schema and required fieldsVariance threshold
Matching workerSKU map, ERP lookup and variance formulaFinal approval policy
Validation workerThreshold and escalation rulesHow the PDF/CSV was parsed

Runnable offline Python

03_supervisor_pattern.py — delegation
class ExtractionAgent:
    def run(self, state):
        state["settlement"] = load_settlement(state["settlement_id"])

class MatchingAgent:
    def run(self, state):
        state["erp_sku"] = map_sku(state["settlement"]["amazon_sku"])
        state["invoice"] = find_invoice(state["erp_sku"])
        state["variance_pct"] = calculate_variance(state)

class ValidationAgent:
    def run(self, state):
        state["decision"] = (
            "MATCHED" if state["variance_pct"] <= 5
            else "HUMAN_REVIEW"
        )

class SupervisorAgent:
    def __init__(self):
        self.workers = [ExtractionAgent(), MatchingAgent(), ValidationAgent()]

    def run(self, settlement_id):
        state = {"settlement_id": settlement_id}
        for worker in self.workers:
            try:
                worker.run(state)
            except (ValueError, KeyError) as error:
                state.update(decision="HUMAN_REVIEW", error=str(error))
                break
        return state
Good design: Give each worker only the tools and data needed for its role. The Validation Agent should not have permission to post a journal entry unless that responsibility is explicitly approved.

6. Hierarchical Supervisor Topology

A hierarchical topology introduces supervisors at multiple levels. The top supervisor coordinates business domains; lower supervisors coordinate specialist workers.

Hierarchical settlement architecture
Reconciliation SupervisorOwns end-to-end goal
↓
Data SupervisorIngestion domain
↓
CSV Worker
+
PDF Worker
Finance SupervisorMatching domain
↓
Invoice Worker
+
Fee Worker
Control SupervisorRisk domain
↓
Validation Worker
+
HITL Worker

When hierarchy is justified

  • Many workers must be grouped by business domain or security boundary.
  • Different teams own ingestion, finance matching and control/approval.
  • A lower-level supervisor can summarize results before sending them upward.
  • The system requires independent scaling or governance per domain.
Trade-off: Every additional supervisor adds model calls, latency, state synchronization, testing work and failure paths. Start with a single agent or one supervisor and introduce hierarchy only when measurements or governance needs justify it.

7. Choosing the Correct Pattern

QuestionPlanner–ExecutorReActSupervisorHierarchical
Primary ideaPlan tasks, then executeDecide, use tool, observe, repeatManager delegates to specialistsManagers coordinate subteams
Best forComplex goal with dependent stepsInformation gathering and tool useClear specialist rolesLarge domain-separated systems
ControlPlan-guidedModel/tool loopSupervisor-guidedLayered supervision
Main riskBad or unnecessary planEndless or unsafe tool loopRouting and aggregation errorsHigh cost and coordination complexity
Essential guardrailValidate plan and step outputsTool allow-list + max iterationsTyped messages + escalationScope, budget, depth and timeout limits
Microsoft Agent Framework mapping: strict settlement stages fit Sequential orchestration; context-based transfer fits Handoff; and complex dynamic planning with a manager fits Magentic orchestration. Prefer the lowest orchestration complexity that reliably solves the problem.

Quick decision guide

  • Known fixed steps? Use a deterministic workflow or sequential orchestration.
  • Agent must repeatedly look up missing facts? Use a bounded ReAct-style tool loop.
  • Several specialized roles? Use a supervisor.
  • Multiple independently governed domains? Consider hierarchy.

11. Interview Questions and Answers

1. What is the difference between a planner and an executor?

The planner decomposes a goal into tasks and orders them. The executor performs each task, records outputs and reports success or failure.

2. What does ReAct mean?

It is a pattern that interleaves a model decision with an action, usually a tool call, and an observation of that action’s result.

3. Why is a maximum iteration limit important?

It prevents infinite loops, controls cost and latency, and creates a predictable escalation path when progress stops.

4. What is a supervisor agent?

An agent responsible for selecting workers, delegating tasks, monitoring progress, aggregating results and handling exceptions.

5. Supervisor vs hierarchical supervisor?

A supervisor directly manages workers. A hierarchical supervisor manages sub-supervisors, which then manage domain-specific workers.

6. When should you avoid a multi-agent design?

When a function, fixed workflow or single agent meets the requirement. Multi-agent systems add coordination, latency, cost, security surfaces and testing complexity.

7. How do workers exchange reliable data?

Use structured, validated schemas with required fields, correlation IDs, clear error states and access controls.

8. What is shared state?

The controlled workflow data available across steps, such as settlement ID, mapped SKU, invoice amount, variance and decision.

9. How do you secure agent tools?

Use least privilege, allow-listed tools, managed identity or approved credentials, input validation, approval gates, audit logs and timeouts.

10. How is a ReAct loop different from a fixed workflow?

A ReAct agent decides the next action from current observations. A fixed workflow’s next step is predetermined by code or graph edges.

11. What happens if a worker fails?

The supervisor should catch the error, record context, retry only when safe, route to another worker if appropriate, or escalate to a human.

12. Which Microsoft Agent Framework orchestration is closest to dynamic manager planning?

Magentic orchestration uses a manager to coordinate specialists, track progress and adapt the plan for complex open-ended tasks.

13. Which orchestration fits a strict extraction → matching → validation pipeline?

Sequential orchestration, or an explicit deterministic workflow, because execution order is known.

14. Why use a deterministic offline demo first?

It makes roles and control flow visible, avoids credentials and cost, and produces repeatable classroom results.

15. What evidence should accompany HUMAN_REVIEW?

Settlement and invoice identifiers, values compared, calculated variance, missing data, tool errors, confidence or rule result, and an audit correlation ID.
