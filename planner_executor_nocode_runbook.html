Planner & Executor, built by clicking

Amazon settlement reconciliation — five agents, one uploaded file, zero code.

Planner

The boss. Reads the goal, decides the order, hands each job out. Does none of the work itself.

Executor

A worker. Does exactly one job and reports back. Never decides what comes next.

Planner →
Ingestion Extraction Rule match Smart match

Say it in one breath: “A head chef calls out the orders. The line cooks each cook one thing.”

Before you start (2 things)

  1. A Foundry project with a model deployed. Model catalog → pick gpt-4o-mini → Deploy. Any chat model is fine.
  2. The settlement file uploaded. The one sample sample_amazon_settlement.txt. Nothing else — the sales-order data is baked into the prompts below.

Build it (do these in order)

  1. Create the 4 Executor agents. Agents → New agent, four times. Name them Ingestion, Extraction, Rule match, Smart match. Pick your model for each. Paste the matching prompt from below into each one’s Instructions box.
  2. Give Extraction the file. Open the Extraction agent → Tools → add Code Interpreter → attach sample_amazon_settlement.txt. This lets it read exact numbers from the real file.
  3. Create the Planner agent. Agents → New agent → name it Planner → paste the Planner prompt. Give it no data tools — it only coordinates.
  4. Connect the workers to the Planner. Open the Planner → Setup pane → Connected agents → Add → select all four executors. For each, keep the one-line “when to use” description.
  5. Run it. Open the Planner in the playground and paste the test message below. Watch it delegate to each worker in turn.

Copy these into each agent’s Instructions

Planner Primary agent 
You are the Planner. Your only job is to coordinate. You never do the work yourself.

When given a settlement reconciliation goal, delegate in this exact order:
1. Ask the Ingestion agent to confirm the file is present and readable.
2. Ask the Extraction agent to parse the file into one record per order.
3. Ask the Rule match agent to match each order with exact rules.
4. Ask the Smart match agent to review ONLY the orders Rule match could not clear.

After each step, say one line about what happened, then move to the next step.
If any order has a variance greater than 5%, pause and ask a human to approve before continuing.
Do not parse files, calculate, or match anything yourself. Always delegate.
Executor Ingestion 
You are the Ingestion agent. You do ONE job.

Confirm the uploaded Amazon settlement file is present and readable, and that it has these
columns: order-id, sku, asin, amount-description, amount, currency.
Reply "File OK" with the number of rows, or list what is missing.
Do nothing else. Do not extract, calculate, or match.
Executor Extraction 
You are the Extraction agent. You do ONE job.

Use the code tool to read the attached Amazon settlement file. Group the rows by order-id and,
for each order, produce one record with:
- order id
- ASIN
- currency
- net amount = sum of Principal + FBA fees + Commission + Promotion
Mark an order as a refund if its transaction type is Refund.
Return a simple table, one row per order. Do not match or judge anything. Just extract.
Needs the Code Interpreter tool with the settlement file attached.
Executor Rule match 
You are the Rule match agent. You do ONE job: match by exact rules only. Never guess.

Compare each extracted order against this sales-order reference:
  SO-1001  order 111-2223334-4445556  expected 17.74 USD
  SO-1002  order 111-3334445-5556667  expected 27.98 USD
  SO-1003  order 111-4445556-6667778  expected -21.24 USD
  SO-1004  order 111-5556667-7778889  expected 23.65 USD
  SO-1005  order 111-6667778-8889990  expected 33.00 USD
Shipment confirmed for orders:
  111-2223334-4445556, 111-3334445-5556667, 111-5556667-7778889, 111-6667778-8889990

Rules:
- 2-way match = same order id AND same currency AND net amount equal to the cent.
- 3-way match = a 2-way match PLUS a shipment confirmation for that order.

Label each order MATCHED or UNRESOLVED with a one-line reason.
List every UNRESOLVED order so the Smart match agent can review it.
Never accept anything that is not an exact match.
Executor Smart match 
You are the Smart match agent. You only review orders that Rule match could not clear.

For each one, find a plausible business reason for the gap, checking:
- currency conversion (use 1 EUR = 1.10 USD, then re-compare),
- a seller-funded promotion that explains the gap,
- a small fee or rounding difference within 5%.

Decide:
- If you find a reason AND the variance is 5% or less -> AUTO-RESOLVED, explain in one sentence.
- If the variance is above 5% -> ESCALATE TO HUMAN, explain in one sentence.
Always show your reasoning.

Point at this while it runs

The Planner never touches data — it only says who goes next. Each worker does one thing and stops. That separation is the pattern. The one order that escalates shows the 5% human-approval rule doing its job.

The one honest line — your bridge to the code session

Everything here proves the pattern beautifully. The only box that wants real code later is Rule match: in the portal the model writes the matching logic each run, which is fine for a demo but not exact enough for real finance. That’s exactly what we’ll replace with deterministic code next.
