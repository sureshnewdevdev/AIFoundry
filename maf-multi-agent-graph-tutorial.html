00

Overview & setup

Microsoft Agent Framework is the open-source SDK and runtime for building agents and multi-agent workflows, with the same concepts across Python and .NET. It is the direct successor to Semantic Kernel and AutoGen, folding AutoGen's simple agent abstractions into Semantic Kernel's enterprise features (typed state, middleware, telemetry) and adding a graph-based workflow engine.

Two layers you'll use together

  • Agents — stateful, multi-turn units: a model + instructions + tools. An agent keeps invoking tools until it can return a final answer.
  • Workflows — a typed, directed graph that routes data along edges and activates executors when their inputs are ready. This is where you assemble the multi-agent system deterministically. An agent can itself be an executor inside the graph.

The graph primitives

  • Executor — a single-responsibility node (wrap an agent, a function, or a sub-workflow).
  • Edge — a routing rule connecting executors; edges can carry conditions for dynamic routing.
  • Event — the observable signals the runtime streams as it runs (great for tracing).
  • Superstep model — execution runs in Pregel-style supersteps: every executor with pending input runs in parallel, then a synchronization barrier waits for all to finish before advancing.

For the 90% case there are five ready-made orchestration builders on top of these primitives — Sequential, Concurrent, Handoff, Group Chat, and Magentic. This tutorial goes one level lower and builds the graph explicitly with WorkflowBuilder, because that's what gives you the deterministic, auditable path enterprises need.

01

Program & assemble the graph

We'll build a settlement-reconciliation flow: a Planner routes work, an Ingestion node loads the raw statements, an Extractor pulls structured fields, and an Executor/Reconciler does the matching. A conditional edge escalates high-risk cases to a human (covered in section 2).

Planner──▶ Ingestion──▶ Extractor──▶ Reconciler──▶ Human approval*

Step 1 — a chat client and some agents

graph.py 
import asyncio
from agent_framework import WorkflowBuilder
from agent_framework.azure import AzureAIAgentClient
from azure.identity import AzureCliCredential

chat = AzureAIAgentClient(async_credential=AzureCliCredential())

planner = chat.create_agent(
    name="Planner",
    instructions="Classify the incoming settlement batch and decide the route.",
)
ingestion = chat.create_agent(
    name="Ingestion",
    instructions="Load and normalise the raw settlement statement text.",
)
extractor = chat.create_agent(
    name="Extractor",
    instructions="Extract trade id, amount, currency, and counterparty as JSON.",
)
reconciler = chat.create_agent(
    name="Reconciler",
    instructions="Match extracted records against the ledger; flag breaks.",
)

Step 2 — wire the executors into a directed graph

The WorkflowBuilder sets a start executor and connects nodes with add_edge. Agents are used directly as executors. .build() returns an immutable, validated Workflow.

graph.py (continued) 
workflow = (
    WorkflowBuilder()
    .set_start_executor(planner)
    .add_edge(planner, ingestion)
    .add_edge(ingestion, extractor)
    .add_edge(extractor, reconciler)
    .build()
)

Step 3 — run it and stream events

graph.py (continued) 
async def main():
    batch = "Settlement batch #4471 — 3 statements attached..."
    async for event in workflow.run_stream(batch):
        if event.type == "output":
            print(event.data)

asyncio.run(main())

Conditional routing & fan-in

Edges can carry conditions, and a switch-case group scales better than many boolean edges. Use a fan-in to wait for several branches before an aggregator runs.

routing.py 
from agent_framework import Case, Default

# Conditional edge: only high-value breaks go to the human path
builder.add_edge(reconciler, human_review,
                 condition=lambda r: r.amount >= 1_000_000)

# Switch-case group with a default safety net
builder.add_switch_case_edge_group(
    planner,
    [
        Case(condition=lambda x: x.kind == "equities", target=equities_flow),
        Case(condition=lambda x: x.kind == "fx",       target=fx_flow),
        Default(target=manual_triage),
    ],
)

# Fan-in: aggregate parallel workers before reporting
builder.add_fan_in_edges([worker_a, worker_b, worker_c], aggregator)
Superstep gotcha to warn students about Within a fan-out, the graph won't advance to the next superstep until every triggered executor in the current step finishes. If one branch is a long chain and another is a single slow node, the chain waits. For truly independent parallel paths, consolidate sequential steps into one executor.
02

Safety rules, PII redaction & human escalation

MAF gives you three complementary hooks: middleware (intercept every request/response), request-info / approval executors (pause the graph for a human), and platform guardrails (Azure AI Content Safety, Foundry Control Plane).

Guardrail + PII-redaction middleware

Middleware wraps agent or function calls so you can inspect and rewrite messages before and after the model runs. This is the natural home for embedding safety rules and stripping PII from outputs.

middleware.py 
import re

PII = [
    (re.compile(r"\b\d{16}\b"),               "[CARD]"),
    (re.compile(r"\b[\w.]+@[\w.]+\.\w+\b"),    "[EMAIL]"),
    (re.compile(r"\b\d{3}-\d{2}-\d{4}\b"),      "[SSN]"),
]

def redact(text: str) -> str:
    for pattern, tag in PII:
        text = pattern.sub(tag, text)
    return text

async def safety_middleware(context, next):
    # --- pre: block disallowed intents before the model runs ---
    user_text = context.messages[-1].text
    if "wire funds" in user_text.lower():
        context.result = "Blocked: fund-transfer requests require the approval path."
        return

    await next(context)          # run the agent

    # --- post: redact PII from whatever the agent produced ---
    if context.result and context.result.text:
        context.result.text = redact(context.result.text)

# Attach when creating the agent
extractor = chat.create_agent(
    name="Extractor",
    instructions="...",
    middleware=[safety_middleware],
)

Human escalation (human-in-the-loop)

MAF workflows support pausing for human input: a node emits a request-info event, the workflow checkpoints and suspends, and it resumes when your app supplies the human's decision. Wire it behind the conditional edge from section 1 so only high-risk cases stop for approval.

escalation.py 
from agent_framework import RequestInfoExecutor, RequestInfoEvent

approval = RequestInfoExecutor(name="HumanApproval")

builder.add_edge(reconciler, approval,
                 condition=lambda r: r.risk == "high")
builder.add_edge(approval, reconciler)   # resume after decision

async for event in workflow.run_stream(batch):
    if isinstance(event, RequestInfoEvent):
        # Surface to a reviewer, then resume with their answer
        decision = await ask_human(event.data)
        await workflow.send_response(event.request_id, decision)
Never log PII in production MAF logging/telemetry only includes message content when you explicitly enable it. At Trace log level, or with ENABLE_SENSITIVE_DATA=true, the full chat messages (including PII) are captured. Keep both off in production — this is a common accidental data-leak path.
  • Layer defenses: middleware in code, plus Azure AI Content Safety filters on the model, plus Foundry Control Plane guardrails to govern a whole fleet of agents.
  • Treat serialized agent sessions as sensitive — restoring one from an untrusted source is accepting untrusted input.
  • For deterministic anti-exfiltration, look at FIDES information-flow-control middleware that enforces policy before sensitive tools run.
03

Automated testing, red-teaming & tracing

Automated evaluation (the test suite)

Use the Azure AI Evaluation SDK to score your graph against a labelled dataset — quality, groundedness, and agent-specific metrics like intent resolution and tool-call accuracy. Run it in CI so a regression fails the build.

evaluate.py 
from azure.ai.evaluation import evaluate, GroundednessEvaluator, RelevanceEvaluator

results = evaluate(
    data="testset.jsonl",                # prompts + expected answers
    evaluators={
        "groundedness": GroundednessEvaluator(model_config),
        "relevance":    RelevanceEvaluator(model_config),
    },
)
print(results["metrics"])
assert results["metrics"]["groundedness.gpt_groundedness"] >= 4.0

Red-teaming (adversarial testing)

The AI Red Teaming Agent uses Microsoft's open-source PyRIT to simulate attacks — including obfuscated prompts that slip past a model's built-in alignment — and scores each attack/response pair to produce an Attack Success Rate (ASR) and a scorecard by risk category.

redteam.py 
from azure.ai.evaluation.red_team import RedTeam, RiskCategory, AttackStrategy

red_team = RedTeam(
    azure_ai_project=project,
    credential=AzureCliCredential(),
    risk_categories=[RiskCategory.SensitiveDataLeakage,   # PII leaks
                     RiskCategory.ProhibitedActions,      # unapproved actions
                     RiskCategory.HateUnfairness],
    attack_strategies=[AttackStrategy.Base64, AttackStrategy.Flip],
)

scan = await red_team.scan(target=my_agent_callback)
print("Attack success rate:", scan.attack_success_rate)

Red-team results log to Foundry so you can track them over time and gate a release on the scorecard. Best run with a human-in-the-loop confirming your prohibited-action taxonomy.

Tracing (OpenTelemetry)

MAF has built-in OpenTelemetry instrumentation. Point it at Azure Monitor Application Insights and you get one end-to-end timeline per task — every model call, tool invocation, and agent decision across the graph.

tracing.py 
from agent_framework.observability import setup_observability

setup_observability(
    applicationinsights_connection_string="<APP_INSIGHTS_CONNECTION_STRING>",
)
# Env-var controls:
#   ENABLE_INSTRUMENTATION=true    (default on)
#   ENABLE_SENSITIVE_DATA=false    (keep OFF in prod)
#   ENABLE_CONSOLE_EXPORTERS=true  (handy locally)
Local debugging For fast iteration, run the graph under the MAF DevUI / VS Code extension to watch executor timelines and inputs/outputs step by step before you ship traces to the cloud.
04

Automated production deployment

Once the graph passes evals and the red-team scorecard, deploy to Foundry hosted agents — the framework adds hosting with only a couple of extra lines. On deploy, the agent gets its own Microsoft Entra identity, so every action is traceable and runs under scoped permissions.

deploy.py 
# Same workflow you built and tested — now hosted on Foundry
from agent_framework.azure import FoundryHostedAgent

hosted = FoundryHostedAgent.from_workflow(workflow, name="settlement-recon")
await hosted.deploy(project=project)   # scoped identity assigned automatically

Gate the pipeline (CI/CD)

Make deployment hands-off but safe: only ship if evaluation thresholds and the red-team ASR pass. Foundry's observability integrates with CI/CD, auto-generated test datasets, and vulnerability detection.

.github/workflows/deploy.yml 
jobs:
  ship:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - run: pip install agent-framework azure-ai-evaluation
      - run: python evaluate.py      # fails build if metrics regress
      - run: python redteam.py       # fails build if ASR too high
      - run: python deploy.py        # only runs if the gates pass

After deployment — keep watching

  • Continuous evaluation — score a sampled slice of live traffic for quality and safety.
  • Scheduled red teaming — recurring adversarial probes against production on synthetic data.
  • Azure Monitor alerts — page someone when outputs breach quality thresholds or produce harmful content; watch for drift and regressions.
  • Foundry Control Plane — unified dashboards, scoped policies, guardrails, and bulk remediation across your whole agent fleet.
The lifecycle in one line Build the graph → add guardrails, PII redaction & escalation → evaluate + red-team + trace → gate CI/CD → deploy to Foundry with a scoped identity → monitor, continuously evaluate, and re-red-team on a schedule.

Interview Q&A

What is the difference between an agent and a workflow in MAF?
An agent is a stateful, multi-turn unit (model + instructions + tools) that reasons and calls tools until it returns an answer. A workflow is a typed, directed graph of executors connected by edges that routes data deterministically. The LLM reasons inside a node; it doesn't control the overall path. An agent can be used as an executor inside a workflow.
Explain the superstep (Pregel/BSP) execution model.
Execution runs in discrete supersteps. In each superstep, every executor that has pending input runs in parallel; then a synchronization barrier waits for all of them to finish before the graph advances and routes the newly emitted messages. The practical consequence is that a fan-out doesn't progress until the slowest branch in the current step completes.
How do you do conditional routing between executors?
Attach a condition to an edge (add_edge with a condition lambda), or use a switch-case edge group with ordered Cases and a Default target. The default is a safety net that catches unexpected values, which matters for auditability.
Where do you put PII redaction and safety rules?
In middleware. MAF middleware wraps agent/function calls so you can inspect and rewrite messages before the model runs (block disallowed intents) and after it runs (redact PII from outputs). Layer this with Azure AI Content Safety filters and Foundry Control Plane guardrails for defense in depth.
How is human-in-the-loop implemented?
A node emits a request-info event; the workflow checkpoints and suspends, then resumes when your application sends the human's response back with the request id. Put it behind a conditional edge so only high-risk cases stop for approval, keeping the common path automated.
What's the risk with sensitive-data logging?
MAF only logs message content when explicitly enabled. At Trace level or with ENABLE_SENSITIVE_DATA=true, the full chat messages — including PII, function arguments, and results — are captured. These must stay off in production; leaving them on is a direct data-leak path.
What does the AI Red Teaming Agent do, and what is ASR?
It automates adversarial probing using Microsoft's PyRIT framework across risk categories (e.g., sensitive-data leakage, prohibited actions, hate/unfairness), applying attack strategies that can bypass a model's built-in alignment. It scores each attack/response pair to produce an Attack Success Rate — the fraction of attacks that succeeded — plus a scorecard you can gate a release on.
How does tracing work in MAF?
MAF has built-in OpenTelemetry instrumentation. You configure observability (e.g., an Application Insights connection string) and it emits spans for model calls, tool invocations, and agent decisions, giving one end-to-end timeline per task in Azure Monitor. Env vars ENABLE_INSTRUMENTATION, ENABLE_SENSITIVE_DATA, and ENABLE_CONSOLE_EXPORTERS control it.
What changes when you deploy to Foundry hosted agents?
Hosting takes only a couple of extra lines. On deploy, the agent receives its own Microsoft Entra identity, so every action is traceable back to that agent and runs under scoped permissions — the basis for governance and isolation at fleet scale.
How do you make deployment automated but safe?
Gate CI/CD on results: run the Azure AI Evaluation SDK and a red-team scan as pipeline steps, and only run the deploy step if metrics and ASR pass. After release, add continuous evaluation on sampled traffic, scheduled red teaming, and Azure Monitor alerts for drift and harmful output.
