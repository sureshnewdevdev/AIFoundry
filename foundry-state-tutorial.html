0 Learning objectives

1 The mental model: three layers of state

A raw chat-completions call is stateless — the model sees only what you send and forgets everything after. Foundry adds state in three progressively more durable layers. Enable only what you need.

LayerWhat it remembersLifetimeEnable by…
① Session state
(threads, runs, messages)		The current conversation — every message, tool call, and resultUntil the thread is explicitly deletedDoing nothing extra — it's on by default when you use a thread
② Persisted thread storageWhere those threads physically liveManaged by you (Standard) or Microsoft (Basic)Choosing Standard setup / Bring-Your-Own Cosmos DB
③ Long-term memory previewDurable, per-user facts distilled from many conversationsUntil it expires (TTL) or you delete itCreating a Memory Store + attaching the memory tool
Key idea: "Enabling state" almost always means moving up a layer — from an automatic thread, to threads in your own database, to a semantic memory that survives across conversations.

2 Architecture graph

How a single user turn flows through the three layers. Ephemeral session context stays in the thread; distilled facts get promoted into the Memory Store, partitioned by scope.

Read the graph as a promotion pipeline: a message enters the thread (①), the thread is persisted to Cosmos (②), and only the durable, distilled facts get promoted into the Memory Store (③) so a brand-new conversation can recall them.

3 Layer ① — Session state (it's already on)

Foundry Agent Service supports persistent threads, runs, and messages. When you create a thread and append messages, the conversation history is maintained and truncated automatically to fit the model's context window — you don't hand-manage it.

The lifecycle

  1. Create an agent — the reasoning entity with instructions and tools.
  2. Create a thread — one per conversation; append messages as the user replies.
  3. Send messages — from the user and the agent (text, images, files).
  4. Run the agent — it processes the thread and appends its response.
  5. Monitor + get response — poll the run to completion, then read the reply.
# pip install azure-ai-projects azure-identity
import os
from azure.ai.projects import AIProjectClient
from azure.identity import DefaultAzureCredential

project = AIProjectClient(
    endpoint=os.environ["FOUNDRY_PROJECT_ENDPOINT"],  # https://<acct>.services.ai.azure.com/api/projects/<proj>
    credential=DefaultAzureCredential(),
)

# A thread IS your session state — history is kept automatically
thread = project.agents.threads.create()
project.agents.messages.create(thread_id=thread.id, role="user",
                               content="Reconcile settlement batch #4471.")

run = project.agents.runs.create_and_process(thread_id=thread.id, agent_id=agent.id)
# The thread now holds the full turn-by-turn history until you delete it.
Two truths to remember: (1) history is automatic within a thread; (2) a new thread starts blank — sessions are stateless relative to each other. Cross-conversation recall is Layer ③, not Layer ①.

4 Layer ② — Persisting threads (Basic vs Standard)

Threads persist until explicitly deleted — but where they live depends on how your project's Agent Service is set up.

Basic setup
Threads, messages, runs, and files are stored in a secure, Microsoft-managed storage account, logically isolated for your project. Zero infrastructure to run. Least control.
Standard setup
Data is stored in your own Azure resources — conversation state in Azure Cosmos DB, plus Azure AI Search and Storage. Full ownership, custom retention, encryption, and governance.

Bring-Your-Own (BYO) thread storage

The Standard path lets you point thread storage at your own database (Cosmos DB, SQL, Blob, or a vector DB). Pair it with geo-replicated Cosmos DB and Foundry can fail over to a secondary region so threads stay available during an outage.

You want…SetupWhy
A quick demo / POCBasicNothing to provision; MS-managed
Compliance, data residency, CMKStandard (BYO)Data sits in resources you own and audit
Custom retention / encryption policiesStandard (BYO)You apply your own governance frameworks
Regional resilienceStandard + geo-replicated CosmosAuto failover keeps threads reachable
Deletion is explicit. All stateful data persists until you call the delete function with the thread ID. Clearing a run in the Playground does not delete the thread. Plan a retention strategy from day one.
# Housekeeping: threads don't expire on their own
project.agents.threads.delete(thread_id=thread.id)

5 Layer ③ — Long-term memory preview

Memory in Foundry Agent Service is a managed, long-term memory solution. It gives an agent continuity across separate sessions, devices, and workflows — retaining user preferences, distilled history, and personalization.

Core concepts

ConceptMeaning
Memory storePersistent container; defines which info is relevant and how it's processed. Create one per agent.
scopePartition key that isolates memories per user/team. Use {{$userId}} with the memory tool for automatic per-user isolation.
memory_search_preview toolAttached to a prompt agent so it can read/write memories during a conversation.
update_delayDebounce window (seconds) of inactivity before writes commit. Default ≈ 300s (5 min).
default_ttl_secondsRetention. 0 = never expires. Set to match compliance needs.
Memory typesuser_profile, chat_summary, and (latest preview) procedural memory.

Step 1 — Prerequisites

  • A Foundry project + a chat model deployment (e.g. gpt-5.2) and an embedding model (e.g. text-embedding-3-small).
  • RBAC: enable a system-assigned managed identity on the project, then assign the Foundry User role (formerly "Azure AI User").
pip install "azure-ai-projects>=2.3.0" azure-identity

Step 2 — Create the memory store

from azure.ai.projects.models import (
    MemoryStoreDefaultDefinition, MemoryStoreDefaultOptions)

options = MemoryStoreDefaultOptions(
    chat_summary_enabled=True,
    user_profile_enabled=True,
    procedural_memory_enabled=True,
    default_ttl_seconds=30*24*60*60,   # 30-day retention; 0 = never
    user_profile_details="Avoid sensitive data: age, financials, precise location, credentials",
)

definition = MemoryStoreDefaultDefinition(
    chat_model=os.environ["MEMORY_STORE_CHAT_MODEL_DEPLOYMENT_NAME"],
    embedding_model=os.environ["MEMORY_STORE_EMBEDDING_MODEL_DEPLOYMENT_NAME"],
    options=options,
)

store = project.beta.memory_stores.create(
    name="my_memory_store",
    definition=definition,
    description="Procedural memory + 30-day TTL",
)

Step 3 — Attach the memory tool to an agent

from azure.ai.projects.models import (
    MemorySearchPreviewTool, PromptAgentDefinition)

tool = MemorySearchPreviewTool(
    memory_store_name="my_memory_store",
    scope="{{$userId}}",     # per-user isolation, resolved from x-memory-user-id header
    update_delay=300,          # commit after 5 min of inactivity
)

agent = project.agents.create_version(
    agent_name="MyAgent",
    definition=PromptAgentDefinition(
        model=os.environ["MEMORY_STORE_CHAT_MODEL_DEPLOYMENT_NAME"],
        instructions="You are a helpful assistant.",
        tools=[tool],
    ),
)
How scope resolves: with {{$userId}}, Foundry reads the x-memory-user-id request header if present (proxy/backend scenarios); otherwise it falls back to the caller's Microsoft Entra token (tid_oid). No hard-coded IDs.

6 Portal walkthrough — enable RBAC for memory

Do this once so the project can call the Memory Store API.

  1. Azure portal → your project → Resource Management ▸ Identity → toggle on the system-assigned managed identity.
  2. Go to the resource that contains your project → Access control (IAM).
  3. Add ▸ Add role assignment.
  4. Assign Foundry User to the project's managed identity, then Review + assign.
Role rename: Foundry User / Owner / Account Owner / Project Manager were previously Azure AI User / Owner / … . Role IDs and permissions are unchanged — you may still see old names mid-rollout.
No RBAC? For dev only, you can fall back to key-based auth, but role-based access is recommended for anything production.

7 End-to-end: prove cross-session recall

The payoff — the agent remembers a preference stated in one conversation and uses it in a different one.

oai = project.get_openai_client()

# --- Conversation A: user states a preference ---
convA = oai.conversations.create()
oai.responses.create(
    input="I prefer dark roast coffee",
    conversation=convA.id,
    extra_body={"agent_reference": {"name": agent.name, "type": "agent_reference"}},
    # extra_headers={"x-memory-user-id": "user_123"},  # scope to a user
)

# Memories commit after update_delay of inactivity
import time; time.sleep(65)

# --- Conversation B: brand-new thread, no context passed ---
convB = oai.conversations.create()
r = oai.responses.create(
    input="Please order my usual coffee",
    conversation=convB.id,
    extra_body={"agent_reference": {"name": agent.name, "type": "agent_reference"}},
)
print(r.output_text)   # → references dark roast, recalled from memory

Direct "remember / forget" commands

When a user explicitly says remember or forget, the memory tool applies it immediately and returns memory_command_call items in the output — no extra configuration needed. (TTL still applies; a remembered item can still expire.)

Static vs contextual recall: inject static user-profile memories at the start of every conversation (call search_memories with a scope but no items); fetch contextual memories per turn by passing the latest messages.

8 Decision guide — which layer do I actually need?

If your requirement is…Enable
"The bot should remember what we said earlier in this chat."① Just use a thread (already on)
"Threads must live in our database for compliance/CMK."② Standard setup / BYO Cosmos DB
"Survive outages across regions."② Standard + geo-replicated Cosmos
"Remember a user's preferences across separate conversations & devices."③ Memory Store + memory tool
"Per-user isolation with automatic identity."③ scope = {{$userId}}
"Long-running business process over days/weeks."Hosted agents' per-project sandbox ($HOME) or a durable-task extension
Don't over-build. Most chat scenarios need only Layer ①. Add ② for governance, ③ only when you need memory that outlives a conversation.
