Microsoft Foundry · Day 1 · Module A1

Build a Planner–Executor agent workflow, no code

Reconcile Amazon marketplace settlements with five collaborating agents — built entirely by clicking in the Foundry portal. One uploaded file, no other services.

No-code New Foundry portal ~20 minutes Bridges to the code session

The idea

Planner and executor, in one breath

Instead of one agent trying to do everything, you split the work into roles. The whole pattern fits in two sentences:

Planner

The boss. Reads the goal, decides the order, hands each job out. Does none of the work itself.

Executor

A worker. Does exactly one job and reports back. Never decides what comes next.

Planner→
IngestionExtractionRule matchSmart match

Say it out loud: “A head chef calls out the orders. The line cooks each cook one thing.”

The key insight for this lab

In the Foundry portal, you build this as a Workflow. The workflow canvas is the planner — it holds the plan and the order. Each agent node is an executor. Your audience gets to see the plan on screen instead of it hiding inside a prompt.

The scenario

Amazon settlement reconciliation, in four stages

Each stage of the real business process becomes one executor agent:

IngestionConfirm the settlement file arrived and is readable. → ingestion_agent
ExtractionParse the raw line items into one clean net-amount record per order. → extraction_agent
Rule matchDeterministic 2-way / 3-way matching against sales orders — no guessing. → rule_match_agent
Smart matchAI reasoning for only the orders rules couldn't clear. → smart_match_agent

Why this split matters

The clean majority is handled by cheap, exact rules. The reasoning agent only ever touches the exceptions — and anything above a 5% variance escalates to a human. That's the governance backbone of the whole design.

Before you build

1Set up the project

  1. Deploy a model. Model catalog → pick gpt-4o-mini (or any chat model) → Deploy. This powers every agent.
  2. Upload the settlement file. Add the one sample sample_amazon_settlement.txt to your project. Nothing else — the sales-order data is baked into the Rule match prompt.
  3. Confirm you're in New Foundry. Top toolbar → New Foundry toggle ON. The Workflows feature lives here.

The four workers

2Create the executor agents

In the Agents area, create four agents. For each, paste the matching instruction below. Give extraction_agent the Code Interpreter tool with the settlement file attached — that's how it reads exact numbers.

Executor Ingestion
You are the Ingestion agent. You do ONE job.

Confirm the uploaded Amazon settlement file is present and readable, and that it has these
columns: order-id, sku, asin, amount-description, amount, currency.
Reply "File OK" with the number of rows, or list what is missing.
Do nothing else. Do not extract, calculate, or match.
Executor Extraction
You are the Extraction agent. You do ONE job.

Use the code tool to read the attached Amazon settlement file. Group the rows by order-id and,
for each order, produce one record with:
- order id
- ASIN
- currency
- net amount = sum of Principal + FBA fees + Commission + Promotion
Mark an order as a refund if its transaction type is Refund.
Return a simple table, one row per order. Do not match or judge anything. Just extract.
Needs the Code Interpreter tool with the settlement file attached.
Executor Rule match
You are the Rule match agent. You do ONE job: match by exact rules only. Never guess.

Compare each extracted order against this sales-order reference:
  SO-1001  order 111-2223334-4445556  expected 17.74 USD
  SO-1002  order 111-3334445-5556667  expected 27.98 USD
  SO-1003  order 111-4445556-6667778  expected -21.24 USD
  SO-1004  order 111-5556667-7778889  expected 23.65 USD
  SO-1005  order 111-6667778-8889990  expected 33.00 USD
Shipment confirmed for orders:
  111-2223334-4445556, 111-3334445-5556667, 111-5556667-7778889, 111-6667778-8889990

Rules:
- 2-way match = same order id AND same currency AND net amount equal to the cent.
- 3-way match = a 2-way match PLUS a shipment confirmation for that order.

Label each order MATCHED or UNRESOLVED with a one-line reason.
List every UNRESOLVED order so the Smart match agent can review it.
Never accept anything that is not an exact match.
Executor Smart match
You are the Smart match agent. You only review orders that Rule match could not clear.

For each one, find a plausible business reason for the gap, checking:
- currency conversion (use 1 EUR = 1.10 USD, then re-compare),
- a seller-funded promotion that explains the gap,
- a small fee or rounding difference within 5%.

Decide:
- If you find a reason AND the variance is 5% or less -> AUTO-RESOLVED, explain in one sentence.
- If the variance is above 5% -> ESCALATE TO HUMAN, explain in one sentence.
Always show your reasoning.

The plan

3Wire them into a Workflow

This is the part that replaced the old “Connected agents” panel. The workflow chains your existing agents in order.

  1. Build → Create new workflow. Choose Sequential for pre-connected nodes, or Blank to add them yourself. Both work.
  2. Add an agent node. Click the + on the Start node's connector → under Invoke choose Agent. The node sits after Start, joined by an arrow — not inside Start.
  3. Assign an existing agent. In the node editor choose Select existing, search ingestion_agent, pick it. (Don't create new — you already built them.)
  4. Chain the rest. Click + on each node and add Extraction, then Rule match, then Smart match, each as Invoke agent → Select existing. Four nodes in a line.
  5. Save. Click Save and name it. Foundry does not autosave — save after every change or you lose the wiring.

Teaching line

The arrows you just drew are the plan. Point at them and say: “This line is the planner. Each box is an executor.”

Run it

4Test in the chat window

Click Run workflow (or Preview). When it asks for a prompt, paste the goal — this message enters Start and flows down the chain:

Prompt paste to run
Reconcile the uploaded Amazon settlement file against our sales orders.
Validate the file, extract each order's net amount, match them with the rules,
and flag anything that needs a human to approve.

What you should see

SO-1001MATCHED — exact 2-way and 3-way
SO-1002ESCALATE TO HUMAN — promotion, 17.9% > 5%
SO-1003AUTO-RESOLVED — refund, exact amount
SO-1004AUTO-RESOLVED — EUR→USD, 0% variance
SO-1005AUTO-RESOLVED — 0.8% fee gap

If something stalls

Click any node to see its individual output. If Extraction says it can't see the file, the Code Interpreter attachment is on the wrong agent. The file is read only at the Extraction step.

Read the result

5The moments worth narrating

SO-1002 is the star. Smart match found the explanation — a seller-funded promotion — and still refused to auto-resolve, because 17.9% breaks the 5% rule. A plausible reason is not authority to act. The agent understood it and still asked a human. That single line is the whole governance lesson.

SO-1003 shows real reasoning. The refund failed the 3-way check because there's no shipment — but the agent reasoned that a missing shipment is expected for a refund, and cleared it. That's the boundary between the rule executor and the reasoning executor made visible.

SO-1004 and SO-1005 are the everyday auto-resolves: a currency conversion and a sub-threshold fee gap. Boringly correct — which is the point. Humans only ever see the one that matters.

Where this goes next

6The one honest limitation — your bridge to code

The demo proves the pattern beautifully. But notice the numbers drift run to run (17.87% one time, 17.9% another). That's because a model is doing the arithmetic and phrasing. The decisions are right every time; the presentation isn't exact.

For real finance you want the Rule match executor to be deterministic and auditable to the cent. That's a few lines of code, not a prompt:

Day 2 preview deterministic rule match
# Exact, repeatable — no model, no drift
def two_way_match(order, so):
    if order.currency != so.currency:
        return "FAIL", "currency mismatch"
    if order.net == so.expected_net:        # equal to the cent
        return "MATCHED", "exact 2-way"
    return "FAIL", f"gap {order.net - so.expected_net}"

So the arc is: build it no-code to see the pattern, then move it to code so it lasts and never drifts. Same five roles, same logic — now exact.

Keep in mind

Honest notes about the portal

  • The portal moves fast. Labels and locations shift between releases. Click through the current UI once right before you deliver rather than trusting a screenshot.
  • Classic vs New are separate. Agents built in New Foundry don't appear in classic, and vice versa — they're different stores. Stay in New Foundry throughout.
  • “Connected agents” is gone in the new service. It was a classic feature. Workflows (this lab) is the no-code replacement; the A2A tool is the delegation replacement, but it needs code to wire up.
  • The visual workflow designer is preview. It's slated to stop running in-portal after Dec 1, 2026; workflow definitions then run as code (YAML) deployed as a hosted agent. Perfect reason to move to the code version.
  • Model output varies. Exact wording and percentages differ each run. The decisions stay correct; only the presentation drifts.
